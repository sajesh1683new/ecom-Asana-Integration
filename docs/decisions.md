# Implementation decisions

- The previous prototype is preserved in ignored `legacy-prototype/`; this is a fresh application and database.
- Roles are enforced labels, not authentication. The selected role travels in `X-Role`.
- AI runs before targeted human review. Entering human review follows AI completion; leaving it requires all automated findings to be triaged. The example error in the brief about entering human review is interpreted as a leaving-review guard, to avoid a circular dependency.
- F4 never gains a location silently: a human must explicitly map the imported comment to the measured feature text and viewport. Rule findings can independently identify that text before this clarification.
- Screenshots establish visual context; DOM measurements provide explainable values. Neither makes the human defect or release decision.
- Functional checks, actual devices, intended behaviour, content approval, defect acceptance and release approval remain human responsibilities.
- The supplied replacement brief supersedes the earlier prototype. Its exact six comment strings are imported from Mock Asana stories; quoted requirements and original observations are stored separately.
- The local design records are measurable synthetic specifications plus drawn PNG frames. A drawn frame is not a browser screenshot baseline. Baseline approval is explicit and comparisons require matching browser, recipe, profile and design versions.
- Capture scope snapshots include all relevant versions. Rechecks narrow to the clarified element, recipe and viewport, so Premium evidence cannot accidentally stand in for Standard evidence. Hidden elements retain full-page evidence and DOM visibility measurements.
- Consolidation is deterministic mock output in this POC, explicitly recorded as such even with a real vision provider. Suggested relationships never merge rows automatically. Group confirmation requires matching element, popup and viewport and prior human defect acceptance.
- Reviewer-selected batch triage records a separate reasoned audit event for every selected finding. It provides a practical demo workflow without granting AI authority.
- Release gating is deliberately stricter than the minimum brief: every unresolved queue item, untriaged automated claim or running capture blocks approval. A passing condition alone never approves the release.
- Real Asana mode uses an existing configured project. It imports new requests, appends source-tagged summaries, creates only human-confirmed defect subtasks and never edits parent descriptions. Later remote scope changes must be reconciled as a new request; ongoing local review is not silently overwritten. Custom-field failure falls back to a status comment.
- The portable setup installs packages and Chromium once; network-free operation refers to subsequent mock runs. A brand-new environment cannot install uncached packages without network access.
- Stage durations are elapsed intervals between audit events, not active labour. AI rates include untriaged claims in the denominator and are provisional. Manual matching requires the same identified element, recipe and viewport. The supplied pilot reference is labelled separately, with unmeasured preparation explicitly disclosed.
- Maintenance belongs to a suitably skilled person nominated by the QA lead, with a named backup in the team's real process. Versioned recipes, rules and prompts make that handover inspectable; this prototype does not assume a separate automation team.
- Source is separated into React presentation, the frontend HTTP client, FastAPI request validation, backend workflow/integration services and the worker's Playwright capture/analysis layer. A single SQLite worker is sufficient; Redis and production authentication are intentionally outside this local scope.
